# Pinned SDK HTTP-client interoperability

Reviewed 2026-10-14 UTC. Test-only actual C# MCP client/server interoperability inside TestServer, not ChatGPT connectivity, OAuth linking or a live Goblin installation.

`tests/SdkHttpClientChecks.cs` creates the pinned SDK 1.4.1 `HttpClientTransport` and `McpClient` against each isolated fixed/rotating HTTP adapter. It supplies TestServer's handler through the SDK's supported caller-owned `HttpClient` constructor. The fixture explicitly selects `StreamableHttp`, disables OAuth and stream reconnection attempts, supplies no known session, and owns no remote session. There is no AutoDetect/SSE fallback, browser/auth callback, discovery/token exchange or external HTTP client. The observed test handler rejects every request target except the exact synthetic customer `/mcp` URL; it records only request counts and presence of session headers, not credentials or bodies.

The only credential is an ephemeral RSA-signed access-token fixture held in memory, sent through the caller-owned client's bearer header. Changing that header between completed calls tests fresh request identity resolution on the same SDK client; no credential refresh or automatic permission approval is involved. The customer-source double verifies exact issuer/subject/resource/Work ID on each invocation and returns only four status fields, separating grant checks from actual status projections.

Checks cover SDK initialization without Work access/session IDs, single safe tool discovery and exact OAuth scope mirror, four-field status results with bigint precision and UTC time, revoked/ungranted/invalid-ID denial, changed-subject isolation, pre-cancelled calls, fixed target/stateless headers, and rotating pre-tool lease invalidation followed by fresh verification of still-published keys on the next call. These complement existing hand-built JSON-RPC requests and actual SDK stdio/composition/cache checks rather than replacing them. Permission errors carry no reauthorization challenge. Cache flush still is not provider revocation or atomic cancellation of admitted/in-flight reads.

## Authentication-failure increment

Missing, malformed and expired bearer fixtures are now checked both during SDK initialization and on tool calls after successful initialization, in fixed/rotating paths. Each rejected operation must produce one POST/401 with the exact configured resource/scope challenge, `no-store` and the fixed one-field public error body. Work-source calls must remain unchanged. The SDK must surface `HttpRequestException` with Unauthorized status, without either synthetic credential in its error text. Only that classification is accepted, not arbitrary cancellation/timeouts or a generic exception counted as a pass.

The test handler captures the fixed challenge and response-shape flags, not raw response bodies or bearer values. Exact target pin plus one-request/one-401 counts detect attempted OAuth discovery/token exchange, legacy fallback or automatic tool retries. OAuth stays null and stream reconnection attempts zero. A later explicitly supplied valid credential is checked independently; no client-driven login, credential refresh, Work approval or automatic re-execution is introduced. Existing authenticated permission denials remain MCP tool errors without an OAuth challenge.

The tagged [Streamable HTTP session source](https://github.com/modelcontextprotocol/csharp-sdk/blob/v1.4.1/src/ModelContextProtocol.Core/Client/StreamableHttpClientSessionTransport.cs) validates unsuccessful responses in `SendMessageAsync`; initialization sends the first message so connection errors propagate during client creation. TestServer body inspection uses the existing buffered HttpContent API without altering the SDK response. These are specific pinned-client observations, not a guarantee about every client, network failure or ChatGPT's OAuth UI.

Clients/transports are explicitly disposed before host stop with five-second waits and async-using cleanup guards. Caller-owned HTTP clients/handlers, hosts and ephemeral keys are disposed. The suite has a 20-second deadline, HTTP/connection waits five seconds and the enclosing test process a 50-second timeout. No test installation, initial password/verifier or live resource is created.

## Pinned HTTPS key-source composition

OI-020 adds one separate rotating adapter/SDK-client fixture using the actual `CustomerHttpsJwksDocumentSource`, its owned HttpClient, cache and RSA/JWT verifier. Only the friend-only transport is replaced by a mock returning an ephemeral public RSA document; the original fixed/rotating fixtures and their checks remain unchanged. Six new checks cover startup without key/Work access, cold SDK initialization with one exact pinned GET, credential isolation/response disposal, safe cached status read, local revocation and explicit later restoration, and source-owned handler disposal before the outer cleanup guard.

The mock refuses any target/method/body/header shape other than the configured public-key GET and the source's two Accept media types. Thus bearer, cookie, proxy authorization and MCP headers cannot reach it in this fixture. It records only counts/safe-shape/disposal flags, not credential values or incoming request bodies. The key response content is disposed after initialization. Authentication can fetch a key during initialization, before any Work read; later permitted and denied reads reuse that cache without additional GETs. Cache freshness does not grant local Work access.

This verifies composition and ownership, not network privacy guarantees for arbitrary handlers or live TLS/provider behavior. Key transport, Work permissions and data remain synthetic; no real owner authority is used. No OAuth discovery/token exchange, provider login, public listener or platform data is involved. The suite keeps its existing 20-second/five-second deadlines and source's streaming/timeout policies. [OpenAI token-verification guidance](https://developers.openai.com/plugins/build/auth), reviewed 2026-10-14 UTC, leaves resource-server verification and application authorization with the customer server.

OI-021 adds three independent cold hosts for a mocked key redirect, HTTP 503 and malformed HTTP-200 document. Six new checks require SDK creation to fail specifically with Unauthorized HttpRequestException, one exact pinned credential-free key GET and one MCP POST/401 with the fixed resource/scope challenge, safe body and no-store. Work-source calls/reads remain zero. Error text must omit the synthetic bearer, upstream-detail marker and redirect address. Failed response content and source-owned handler disposal are checked independently; failed transports are disposed before host/source cleanup.

The mock now accepts explicit response status/location in addition to its public-key body; successful fixtures retain HTTP 200/no Location. No redirect request is emitted in the mocked composition, but this is not live redirect/TLS evidence. OAuth remains disabled, target pins/one-request counts remain authoritative for this fixture, and a timeout or arbitrary exception is not accepted as a successful denial. Current source/cache classification converts these key failures into sanitized connector authentication failures; production behavior is unchanged. Official failure/challenge guidance was rechecked on 2026-10-14 UTC. Local permission errors remain separate and do not trigger reconsent.

OI-022 adds one deliberate second SDK creation per failed host/cache after disposing the first failed transport. Three new checks require a separate safe POST/401 but keep the key GET count at one and Work calls/reads at zero; both error texts omit the synthetic bearer/source marker/redirect. A test-only frozen `GetTimestamp` keeps cache elapsed time at zero deterministically, while JWT wall-clock validity and cancellation/request/disposal timers remain real. This does not measure production cooldown duration or prove recovery after it. No sleep, automatic reconnect, key refresh or failed Work retry is added. The new transport still has null OAuth, zero reconnection attempts and no session ownership. Source-owned handler/content disposal remains verified after both failed transports are disposed. Official failure/challenge guidance was rechecked on 2026-10-14 UTC.

- [SDK v1 options](https://csharp.sdk.modelcontextprotocol.io/v1/api/ModelContextProtocol.Client.HttpClientTransportOptions.html) and [tagged 1.4.1 source](https://github.com/modelcontextprotocol/csharp-sdk/blob/v1.4.1/src/ModelContextProtocol.Core/Client/HttpClientTransportOptions.cs) document explicit mode, optional OAuth, session ownership and reconnection limits. ## Limits and exchange

Actual client/server wire serialization, request pipeline and RSA/JWT verification are exercised. Keys/owner/grants/Work source remain synthetic and in-memory. No socket, DNS/TLS/provider, real owner session, OAuth consent/PKCE/token flow, durable SQL, ChatGPT/tunnel or Slack end-to-end test is performed. The [primary tool OAuth metadata gap](TOOL-OAUTH-METADATA.md) remains; a compatibility mirror accepted by this C# client does not establish current ChatGPT UI acceptance, public distribution or SIWC eligibility.

No production code, listener, dependency version/lockfile, authoritative customer storage or existing integration changes. A future real connection necessarily exchanges descriptors, OAuth code/token copies and selected Work IDs/status fields with OpenAI, or selected messages/events with Slack. Those platform-held copies are not exclusively on-premises; no Goblin-operated central auth/data service is introduced.
