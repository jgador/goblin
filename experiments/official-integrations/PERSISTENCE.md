# Customer-owned Work read persistence prototype

Reviewed 2026-10-14 UTC against Goblin's current schema, database-first mapping rules, application transaction boundary, and [Npgsql data-source/parameter documentation](https://www.npgsql.org/doc/basic-usage.html). This is an **undeployed query and schema proposal**, not verified durable authorization. There are no PostgreSQL test connections or PostgreSQL tools in this sandbox.

## Implemented boundary

`ICustomerWorkStatusSource.ReadAuthorizedAsync` receives the verified connector identity and positive Work ID. `ConnectorReadBoundary` no longer accepts a separate grant checker and unrestricted Work reader. Only test code retains that split fake. This intentionally changes the experiment's constructor contract; production Goblin and the stdio cookie bridge are unchanged.

`PostgresGrantedWorkStatusSource` accepts a customer-owned `DbDataSource` intended to be Npgsql. It creates one bounded, parameterized SELECT, authorizing issuer/subject/resource/Work ID and projecting only `id`, `version`, `status`, `updated_at` within the same statement. It never reads objective, JSON state, history, messages, artifacts or credentials. Empty results do not distinguish missing Work from missing permission. It rejects invalid IDs, nonpositive versions, unknown/noncanonical statuses and non-UTC timestamps; errors are sanitized. Caller cancellation is preserved and commands/readers are disposed.

Approval must be effective, expiry must be in the future, and revocation must be absent. The query also checks token expiry against the database's [statement timestamp](https://www.postgresql.org/docs/current/functions-datetime.html), not an earlier transaction start. Token verification and local permission are separate requirements; token scope or profile claims never create a grant. Database/application clock synchronization remains necessary.

The single statement avoids a separate grant-check/Work-fetch gap. It is **not** a linearizable revocation barrier: a read whose statement snapshot precedes a concurrent revocation commit may finish. Once a revocation is committed, later read statements must deny it. No grant cache or owner fallback is present. Per-token denylisting, immediate termination of in-flight responses and individual bearer-token revocation are not implemented; local Work grant revocation and token expiry are the current proposed controls.

## Proposed schema, not an installation script

Do not execute this from Web/MCP startup. Do not introduce a second production migration or hand-edit generated EF types. Once an authenticated disposable PostgreSQL profile is available, consolidate reviewed DDL into `backend/database/migrations/0001_initial.sql`, update the singular table/candidate list, regenerate EF using the repository tooling, and commit schema/list/generated mappings together. Until then, this table does not exist in Goblin and the source fails closed.

```sql
CREATE TABLE public.connector_work_read_grant (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    issuer text COLLATE "C" NOT NULL CHECK (octet_length(issuer) BETWEEN 1 AND 512),
    subject text COLLATE "C" NOT NULL CHECK (octet_length(subject) BETWEEN 1 AND 256),
    resource text COLLATE "C" NOT NULL CHECK (octet_length(resource) BETWEEN 1 AND 512),
    work_id bigint NOT NULL REFERENCES public.work_item(id) ON DELETE CASCADE,
    approved_at timestamptz NOT NULL,
    expires_at timestamptz NOT NULL CHECK (expires_at > approved_at),
    revoked_at timestamptz CHECK (revoked_at >= approved_at),
    UNIQUE (issuer, subject, resource, work_id)
);
```

No defaults or seeded approvals. Exact case-sensitive identity/resource matching is intentional. Bounded identity fields keep the composite index small; approve only identities fitting these reviewed limits. The owner approval timestamp is evidence recorded by a future authenticated writer, not proof that an arbitrary database writer is trusted. Do not expose grant mutation to MCP or map external profiles to the local owner.

Future approval/revoke operations must authenticate the existing local owner, require an explicit Work selection and bounded expiry, use Goblin's short application transaction/advisory-lock convention, and record an appropriate customer-local authorization audit. Review audit retention before deleting grants with Work. A revoked/expired row is not automatically renewed. Existing Slack `external_identity`/conversation records are separate and unchanged. A dedicated read-only connector database role could further restrict access to grants and four Work columns; it is not provisioned here.

## Verification and next step

Focused checks execute real RSA/JWT validation and the source's ADO.NET command/projection/error path using a fake data source. They inspect exact SQL policy clauses and typed parameters, including a hostile subject bound as data, command count/timeout/disposal, empty results and malformed rows. **They do not evaluate PostgreSQL SQL, MVCC, constraints, privileges, certificates, restart persistence or revocation.** No mock is registered as a default customer service.

Next: obtain an already provisioned disposable PostgreSQL test profile without interactive login; validate DDL and actual Npgsql parameter/timestamp behavior, durable approval/revoke/expiry and concurrent snapshot semantics. Follow the database-first regeneration workflow before implementing the local-owner writer and composing the HTTP adapter. Keep production listener disabled until those checks and customer IdP authorization are verified.

No central service, connection string, password, migration runner or grant writer is added. Authoritative grants and Work remain customer-local. If connected later, selected Work IDs/status fields still necessarily pass to ChatGPT/OpenAI; OAuth clients handle access tokens. This increment performs no platform exchange.
