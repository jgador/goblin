# Activation and distribution handoff

Reviewed 2026-10-15 UTC against current official documentation and the actual experiment/production entry points. This is an activation decision, not another implementation or an end-to-end result. The existing automation is paused because the next meaningful activation milestone needs unavailable external prerequisites. Resume only with changed evidence; the integration goal is not complete.

## What can be used today

The only MCP server executable in the experiment is [mcp/Program.cs](mcp/Program.cs). Arguments select credential-free offline metadata review; no arguments start stdio with a privately supplied existing local owner session and explicit process-level Work IDs. Neither mode registers a production route. The session bridge is not a remote multi-user authorization solution or a publicly distributed plugin.

[PrivateMcpHttpAdapter](http/PrivateMcpHttpAdapter.cs) is a .NET 10 library with fixed-key and rotating-key composition, not a runnable HTTP deployment. Tests supply synthetic keys, owners, grants and Work sources through TestServer. No experiment registration was found in production `backend/src`, and the proposed grant table is absent from the production baseline migration. Do not confuse a passing SDK client with a connected ChatGPT account.

## Platform decision

| Route | Current official requirement | Verdict and missing evidence |
| --- | --- | --- |
| Customer-specific private ChatGPT connection | [Custom MCP](https://developers.openai.com/api/docs/guides/custom-mcp-server) lets an authorized workspace user configure a server URL or tunnel and its authentication. | Closest supported decentralized approach: one maintained implementation, separately connected per customer. Requires a safe customer host, customer authorization server and workspace access. Not one public directory installation. |
| Private outbound transport | [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) requires a tunnel, runtime key, organization/workspace associations and roles. It does not support public plugin distribution. | A customer-run client avoids inbound public MCP ingress and a Goblin data plane, but OpenAI relays the traffic. It does not implement user authorization or by itself establish authorization-server reachability. No tunnel resources or credentials are provisioned here. |
| One public remote plugin | [Remote review](https://developers.openai.com/plugins/deploy/app-review) requires public endpoints; template URLs are restricted to trusted developers with an established relationship. | A template/review example is not proof of Goblin eligibility, arbitrary customer domains or independent per-instance OAuth settings. Need explicit platform confirmation and an accepted review configuration before implementing this flow. A universal Goblin proxy violates the requested boundary. |
| Public local/desktop plugin | [Desktop submissions](https://developers.openai.com/plugins/deploy/desktop-only) require approved partners/organization allowlisting and local desktop threads. | No approval established. Not a web/mobile replacement. Do not package owner sessions into plugin files. |
| Prefer ChatGPT identity | [Sign in with ChatGPT](https://developers.openai.com/siwc/quickstart) distinguishes limited identity-partner access from open-source ChatGPT-plan usage for inference. | No identity entitlement or client registration is established. Inference credentials are not Goblin access tokens or Work permission. Customer-local account linking and grants would still be necessary. |
| One Slack app with current mentions/DM behavior | [Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/) has app-level credentials, nondeterministic delivery among connections and no public Marketplace listing. [HTTP events](https://docs.slack.dev/apis/events-api/using-http-request-urls/) have one app Request URL across workspaces. | Neither reviewed route proves customer-exclusive direct delivery. Keep the existing customer-owned apps. Filtering after receiving a foreign event is not privacy isolation. |
| Slack distributed OAuth | [PKCE](https://docs.slack.dev/authentication/using-pkce/) supports public clients; desktop redirects cannot request bot scopes and refresh-token lifetime/rotation need a separate design. | Previously reviewed pre-registered customer HTTPS callbacks remain conditional, not arbitrary-domain onboarding or event routing. No official secret/app-level token or app-management credential may be distributed. See [SLACK-REVIEW.md](SLACK-REVIEW.md). |

These are scoped findings from the reviewed routes, not a universal proof that future platform capabilities cannot solve the goal. A public directory entry or identity approval alone would not complete the customer-local authorization implementation.

The smallest justified resumed increment is the existing disposable PostgreSQL test milestone, not a new listener or more synthetic metadata cases. It requires **both** `GOBLIN_TEST_POSTGRES_ADMIN` and `GOBLIN_TEST_POSTGRES_APP` through the existing private test-profile mechanism, matching Host/Port, the harness's exact roles, VerifyFull root/client certificates and create/drop permission on a non-production server. Do not put values, keys or connection strings in Git/chat. The recorded missing binaries/profile blocker was not reprobed, and Docker/Kubernetes availability was not assumed.

After that milestone, implement and verify the local-owner mutation/audit boundary in a separate increment. Obtain customer IdP/TLS and workspace/tunnel access before live linking. Public distribution and ChatGPT identity require their own documented eligibility proof; do not bundle those approvals into database-test success. Slack changes wait for an independent event-delivery/token-lifecycle proof.

## Data and verification limits

Customer-local credentials, configuration, grants, audits and authoritative Work history remain on-premises. A later OAuth client necessarily handles codes and connector-token copies; OpenAI receives MCP descriptors, selected requests/results and any permitted identity attributes. Tunnel traffic passes through OpenAI. Slack holds its app configuration, platform authorization/token records, messages/events/identity metadata and selected replies. These copies are not exclusively on-premises. No Goblin-operated authentication, proxy, event receiver or customer-data store is introduced.

This review fetched documentation and inspected files only. No customer data, credentials or Work were sent to either platform. No installation, password/verifier, provider login, database connection, tunnel or listener was started. Runtime suites were not rerun for prose-only changes; previous 152 metadata/command checks, 392 broad MCP checks and four Slack scope cases remain historical, separate results. Whitespace, relative links/anchors and read-only source assertions are the relevant checks for this handoff, not end-to-end evidence.

The existing integration automation was disabled through its already connected management tool under the user's full-blocker rule. No replacement was created and no other task was changed. Resume it only after a concrete prerequisite changes and continue this branch/state; do not silently restart the same missing-capability probes or expand mock counts to imply readiness.
